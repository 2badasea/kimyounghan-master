## 0. 큰 그림 (먼저 읽기)

지난주(섹션 2~5)까지는 **AppConfig 가 모든 것을 손으로 적었다.**

```java
@Bean
public OrderService orderService() {
    return new OrderServiceImpl(memberRepository(), discountPolicy()); // 무엇을 넣을지 직접 적음
}
```

이번 범위는 이 AppConfig 를 두 방향에서 다시 본다.

1. **섹션 6 — 빈은 몇 개 만들어지나?** 순수 자바 AppConfig 는 호출할 때마다 `new` 로 새 객체를 만든다. 스프링 컨테이너는 빈을 **하나만 만들어 공유**한다(싱글톤). 그래서 생기는 주의점과, AppConfig 코드가 여러 번 호출돼도 객체가 하나인 이유(`@Configuration` 의 비밀)를 다룬다.
2. **섹션 7~8 — 꼭 손으로 적어야 하나?** 빈이 수십·수백 개가 되면 하나하나 적기 번거롭고, 설정 파일이 커지고, 빠뜨리는 일이 생긴다(90쪽). 그래서 스프링은 등록과 주입을 자동으로 해 준다.

| | 지금까지 (수동) | 섹션 7~8 (자동) |
|---|---|---|
| **등록** | 설정 클래스에 `@Bean` 메서드를 하나씩 | 클래스에 `@Component` 만 붙이면 **컴포넌트 스캔**이 찾아서 등록 — **섹션 7** |
| **빈 이름** | 메서드 이름 (`memberService`) | 클래스 이름 첫 글자 소문자 (`memberServiceImpl`) |
| **주입** | AppConfig 가 생성자를 호출하며 직접 넣음 | 생성자에 `@Autowired` → 스프링이 **타입**으로 찾아 넣음 — **섹션 8** |

섹션 8은 이 자동 주입의 세부 규칙이다: 주입 방법 4가지, 주입할 빈이 없을 때, 생성자 주입을 고르는 이유, 롬복, 같은 타입 빈이 2개 이상일 때, 모두 받기(List·Map), 자동과 수동을 나누는 실무 기준.

# 섹션 6. 싱글톤 컨테이너 (PDF 74~89쪽)

## 6-1. 웹 애플리케이션과 싱글톤 (74~75쪽)

**한 줄 요약**: 순수 자바 AppConfig 는 요청할 때마다 객체를 새로 만든다. 웹은 여러 고객이 동시에 요청하므로 낭비가 크다. 해결책은 객체를 **딱 1개만 만들어 공유**하는 것(싱글톤)이다.

```java
@Test
@DisplayName("스프링 없는 순수한 DI 컨테이너")
void pureContainer() {
    AppConfig appConfig = new AppConfig();

    MemberService memberService1 = appConfig.memberService();   // 호출할 때마다 new
    MemberService memberService2 = appConfig.memberService();   // 또 new

    assertThat(memberService1).isNotSameAs(memberService2);     // 참조값이 다르다
}
```

- `memberService()` 는 안에서 `new MemberServiceImpl(...)` 을 하니, 부를 때마다 다른 객체가 나온다.
- 고객 요청이 초당 100번이면 객체도 초당 100개가 만들어졌다 사라진다. **메모리 낭비가 심하다.**
- 🔸 `isSameAs` 는 **같은 객체인지**(`==`, 참조 비교), `isEqualTo` 는 **값이 같은지**(`equals`) 비교한다. 이 절에서는 "같은 객체냐"가 궁금하니 `isSameAs`·`isNotSameAs` 를 쓴다.

## 6-2. 싱글톤 패턴 (75~77쪽)

**한 줄 요약**: 클래스의 인스턴스가 딱 1개만 생기도록 보장하는 디자인 패턴이다. 공유는 되지만 문제가 많아서 **안티패턴**으로도 불린다.

```java
public class SingletonService {

    // 1. static 영역에 객체를 딱 1개만 만들어 둔다
    private static final SingletonService instance = new SingletonService();

    // 2. 객체가 필요하면 이 static 메서드로만 꺼내 간다 — 항상 같은 객체
    public static SingletonService getInstance() {
        return instance;
    }

    // 3. 생성자를 private 으로 막아 외부에서 new 를 못 하게 한다
    private SingletonService() {
    }

    public void logic() {
        System.out.println("싱글톤 객체 로직 호출");
    }
}
```

```java
@Test
@DisplayName("싱글톤 패턴을 적용한 객체 사용")
void singletonServiceTest() {
    // new SingletonService();   // private 생성자라 컴파일 오류

    SingletonService singletonService1 = SingletonService.getInstance();
    SingletonService singletonService2 = SingletonService.getInstance();

    assertThat(singletonService1).isSameAs(singletonService2);   // 같은 객체
}
```

- PDF 는 이 클래스를 **main 이 아닌 test 위치**에 만들라고 한다(실습용).
- 구현 방법은 여러 가지인데, 여기서는 객체를 미리 만들어 두는 가장 단순하고 안전한 방법을 골랐다.

### 싱글톤 패턴의 문제점 (77쪽)

| 문제 | 풀어 보면 |
|---|---|
| 구현 코드가 많이 들어간다 | 클래스마다 위 1·2·3 코드를 반복해야 한다 |
| **DIP 위반** | 쓰는 쪽이 `SingletonService.getInstance()` 처럼 **구체 클래스 이름**을 직접 부른다 |
| OCP 위반 가능성이 높다 | 구체 클래스에 의존하니, 구현을 바꾸면 쓰는 쪽 코드를 고쳐야 한다 |
| 테스트하기 어렵다 / 내부 속성을 바꾸거나 초기화하기 어렵다 | 🔸 객체가 하나라 테스트끼리 상태가 섞이고, 다른 구현(가짜 객체)으로 바꿔 끼울 통로가 없다 |
| 자식 클래스를 만들기 어렵다 | 생성자가 `private` 이다 |
| **결론: 유연성이 떨어진다** | 그래서 안티패턴으로 불리기도 한다 |

> 지난주의 "구현까지 의존하는 문제"(DIP·OCP 위반)가 싱글톤 패턴에서도 그대로 생긴다는 점에 주목하자.

## 6-3. 싱글톤 컨테이너 (78~79쪽)

**한 줄 요약**: 스프링 컨테이너는 싱글톤 패턴 코드 없이도 빈을 **하나만 만들어 관리**한다. 이 기능을 **싱글톤 레지스트리**라고 한다.

```java
@Test
@DisplayName("스프링 컨테이너와 싱글톤")
void springContainer() {
    ApplicationContext ac = new AnnotationConfigApplicationContext(AppConfig.class);

    MemberService memberService1 = ac.getBean("memberService", MemberService.class);
    MemberService memberService2 = ac.getBean("memberService", MemberService.class);

    assertThat(memberService1).isSameAs(memberService2);   // 같은 객체
}
```

- 지금까지 다룬 **스프링 빈이 바로 싱글톤으로 관리되는 빈**이다. 컨테이너 생성 과정에서 객체를 하나만 만들어 빈 저장소에 넣어 두고, 요청이 올 때마다 그 객체를 돌려준다.
- 그래서 싱글톤 패턴의 단점이 사라진다.
  - 싱글톤용 코드(`static instance`, `getInstance()`, `private` 생성자)를 쓰지 않아도 된다.
  - 쓰는 쪽은 인터페이스로 주입받으니 **DIP·OCP·테스트·private 생성자 문제**에서 자유롭다.
- 그림(79쪽): 클라이언트 A·B·C 가 `memberService` 를 요청하면 **같은 `memberService@x01`** 을 받는다.
- 참고: 기본은 싱글톤이지만, 요청할 때마다 새 객체를 주는 방식도 있다 → **빈 스코프**(섹션 10)에서 다룬다.

## 6-4. 싱글톤 방식의 주의점 (79~81쪽) ★

**한 줄 요약**: 여러 클라이언트가 **하나의 객체를 공유**하므로, 싱글톤 빈은 **무상태(stateless)** 로 설계해야 한다.

무상태로 설계한다는 것은:
- 특정 클라이언트에 의존하는 필드가 있으면 안 된다.
- 특정 클라이언트가 값을 바꿀 수 있는 필드가 있으면 안 된다.
- 가급적 읽기만 가능해야 한다.
- 필드 대신 공유되지 않는 **지역변수, 파라미터, ThreadLocal** 을 써야 한다.

### 상태를 유지하면 생기는 문제

```java
public class StatefulService {

    private int price;   // 상태를 유지하는 필드

    public void order(String name, int price) {
        System.out.println("name = " + name + " price = " + price);
        this.price = price;   // 여기가 문제!
    }

    public int getPrice() {
        return price;
    }
}
```

```java
@Test
void statefulServiceSingleton() {
    ApplicationContext ac = new AnnotationConfigApplicationContext(TestConfig.class);
    StatefulService statefulService1 = ac.getBean("statefulService", StatefulService.class);
    StatefulService statefulService2 = ac.getBean("statefulService", StatefulService.class);

    statefulService1.order("userA", 10000);   // ThreadA: A 사용자 10000원 주문
    statefulService2.order("userB", 20000);   // ThreadB: B 사용자 20000원 주문

    int price = statefulService1.getPrice();  // ThreadA: A 의 주문 금액 조회
    assertThat(price).isEqualTo(20000);       // 10000원을 기대했는데 20000원!
}

static class TestConfig {

    @Bean
    public StatefulService statefulService() {
        return new StatefulService();
    }
}
```

- 실제 스레드는 쓰지 않고, ThreadA 가 A 코드를, ThreadB 가 B 코드를 부른다고 가정한 예제다.
- `statefulService1` 과 `statefulService2` 는 **같은 객체**다(싱글톤). 그래서 `price` 필드 하나를 두 사용자가 같이 쓴다.
- B 의 주문이 A 가 넣은 값을 덮어써서, A 는 20000원을 보게 된다.
- 강의자료: 실무에서 이런 경우를 종종 보며, 몇 년에 한 번씩 꼭 만나는 해결하기 어려운 큰 문제가 된다. **"스프링 빈은 항상 무상태로 설계하자."**

🔸 고치는 방법(PDF 에는 코드가 없다): 필드에 저장하지 말고 **값을 반환**해서 호출한 쪽의 지역변수에 담게 한다.

```java
public int order(String name, int price) {
    System.out.println("name = " + name + " price = " + price);
    return price;   // 필드에 저장하지 않는다
}

int userAPrice = statefulService1.order("userA", 10000);   // 지역변수 — 공유되지 않음
```

> 🔸 스프링 입문 발표 퀴즈 2번("스프링 빈은 싱글톤이라 필드에 요청마다 달라지는 값을 저장하면 안 된다")이 이 절이다. 서비스 필드에 `private final` 의존관계만 두는 이유이기도 하다.

## 6-5. `@Configuration` 과 싱글톤 (82~86쪽)

**한 줄 요약**: AppConfig 코드만 보면 `MemoryMemberRepository` 가 여러 번 `new` 될 것 같은데, 실제로는 **딱 1번**만 만들어진다.

```java
@Configuration
public class AppConfig {

    @Bean
    public MemberService memberService() {
        return new MemberServiceImpl(memberRepository());       // memberRepository() 호출 → new?
    }

    @Bean
    public OrderService orderService() {
        return new OrderServiceImpl(memberRepository(), discountPolicy());   // 또 호출 → new?
    }

    @Bean
    public MemberRepository memberRepository() {
        return new MemoryMemberRepository();
    }
}
```

**이상한 점**: `memberService()` 와 `orderService()` 가 각각 `memberRepository()` 를 부르니, 서로 다른 `MemoryMemberRepository` 가 2개 생겨서 싱글톤이 깨질 것 같다.

### 확인 1 — 주입된 객체가 같은가?

```java
// 테스트 용도로 구현 클래스에만 조회 메서드 추가 (인터페이스에는 추가하지 말 것)
public MemberRepository getMemberRepository() {
    return memberRepository;
}
```

```java
@Test
void configurationTest() {
    ApplicationContext ac = new AnnotationConfigApplicationContext(AppConfig.class);
    MemberServiceImpl memberService = ac.getBean("memberService", MemberServiceImpl.class);
    OrderServiceImpl orderService = ac.getBean("orderService", OrderServiceImpl.class);
    MemberRepository memberRepository = ac.getBean("memberRepository", MemberRepository.class);

    assertThat(memberService.getMemberRepository()).isSameAs(memberRepository);   // 같다
    assertThat(orderService.getMemberRepository()).isSameAs(memberRepository);    // 같다
}
```

→ 세 곳 모두 **같은 인스턴스**를 쓰고 있다.

### 확인 2 — 몇 번 호출되나?

각 `@Bean` 메서드에 `System.out.println("call AppConfig.xxx")` 를 넣고 실행하면, `memberRepository()` 는 3번 호출될 것 같다.
1. 컨테이너가 빈으로 등록하려고 `memberRepository()` 호출
2. `memberService()` 안에서 호출
3. `orderService()` 안에서 호출

그런데 실제 출력은 **모두 1번씩**이다.

```
call AppConfig.memberService
call AppConfig.memberRepository
call AppConfig.orderService
```

> 지난주 발표 범위 57쪽의 "단순히 자바 코드를 호출하는 것 같지만, 차이가 있다. 이 차이는 뒤에 싱글톤 컨테이너에서 설명한다"의 답이 다음 절이다.

## 6-6. `@Configuration` 과 바이트코드 조작의 마법 (86~89쪽) ★

**한 줄 요약**: 스프링은 **CGLIB** 라는 바이트코드 조작 라이브러리로 **AppConfig 를 상속한 자식 클래스**를 만들어 빈으로 등록한다. 그 자식 클래스가 "이미 빈이 있으면 그걸 돌려주는" 코드로 바꿔 놓아서 싱글톤이 보장된다.

```java
@Test
void configurationDeep() {
    ApplicationContext ac = new AnnotationConfigApplicationContext(AppConfig.class);

    AppConfig bean = ac.getBean(AppConfig.class);   // AppConfig 도 스프링 빈으로 등록된다
    System.out.println("bean = " + bean.getClass());
}
```

```
bean = class hello.core.AppConfig$$EnhancerBySpringCGLIB$$bd479d70
```

- `AnnotationConfigApplicationContext` 에 넘긴 클래스는 스프링 빈으로 등록된다. 그래서 AppConfig 도 빈이다.
- 순수한 클래스라면 `class hello.core.AppConfig` 가 찍혀야 한다. 그런데 이름 뒤에 **CGLIB** 가 붙었다.
  - 내가 만든 AppConfig 가 아니라, 스프링이 **AppConfig 를 상속받은 다른 클래스**를 만들어 빈으로 등록한 것이다.
  - 그래서 `AppConfig` 타입으로 조회해도 꺼내진다(자식 타입이니까).
- 🔸 스프링 부트 3(스프링 6)에서는 이름이 `AppConfig$$SpringCGLIB$$0` 처럼 강의 출력과 조금 다르게 찍힐 수 있다. "CGLIB 가 붙은 자식 클래스"라는 점은 같다.

### 자식 클래스가 하는 일 (87쪽, 개념 코드)

```java
@Bean
public MemberRepository memberRepository() {
    if (memoryMemberRepository 가 이미 스프링 컨테이너에 등록되어 있으면) {
        return 스프링 컨테이너에서 찾아서 반환;
    } else {   // 컨테이너에 없으면
        기존 로직을 호출해서 MemoryMemberRepository 를 생성하고 스프링 컨테이너에 등록;
        return 반환;
    }
}
```

- `@Bean` 이 붙은 메서드마다 이런 코드가 **동적으로** 만들어진다. 그래서 `memberRepository()` 를 몇 번 불러도 같은 객체가 돌아온다.
- 실제 CGLIB 내부 기술은 훨씬 복잡하다. 위 코드는 이해를 돕는 그림이다.

### `@Configuration` 없이 `@Bean` 만 쓰면? (88~89쪽)

```java
// @Configuration 삭제
public class AppConfig {
    // @Bean 메서드는 그대로
}
```

```
bean = class hello.core.AppConfig          ← CGLIB 없이 순수한 AppConfig

call AppConfig.memberService
call AppConfig.memberRepository
call AppConfig.orderService
call AppConfig.memberRepository
call AppConfig.memberRepository            ← memberRepository() 가 3번 호출됨
```

- 1번은 컨테이너가 빈으로 등록하려고, 나머지 2번은 `memberService()`·`orderService()` 가 직접 불러서 호출됐다.
- 그 결과 세 곳의 `MemoryMemberRepository` 가 **모두 다른 인스턴스**가 되고, 확인 1 의 테스트는 실패한다.
- 확인이 끝나면 `@Configuration` 을 다시 붙여 두자.

### 정리 (88~89쪽)

- `@Bean` 만 써도 스프링 빈으로 **등록은 된다.** 하지만 `memberRepository()` 처럼 의존관계 주입 때문에 **메서드를 직접 호출할 때 싱글톤이 보장되지 않는다.**
- 고민할 것 없다. **스프링 설정 정보에는 항상 `@Configuration` 을 쓰자.**

> 섹션 7 표(7-2)의 "`@Configuration` — 스프링 빈이 싱글톤을 유지하도록 추가 처리"가 바로 이 CGLIB 처리다.

# 섹션 7. 컴포넌트 스캔 (PDF 90~101쪽)

## 7-1. 컴포넌트 스캔과 의존관계 자동 주입 시작하기 (90~94쪽)

**한 줄 요약**: 설정 클래스에 `@ComponentScan` 을 붙이면, `@Component` 가 붙은 클래스를 스프링이 찾아 빈으로 등록한다. 무엇을 넣을지는 각 클래스의 생성자에 `@Autowired` 로 표시한다.

### 설정 클래스 — `@Bean` 이 하나도 없다

```java
@Configuration
@ComponentScan(
        excludeFilters = @Filter(type = FilterType.ANNOTATION, classes = Configuration.class))
public class AutoAppConfig {
}
```

- `@ComponentScan`: 이 설정 클래스가 있는 패키지부터 아래로 훑어서 `@Component` 가 붙은 클래스를 빈으로 등록하라는 표시다.
- **`excludeFilters` 로 `@Configuration` 을 뺀 이유**
  - `@Configuration` 안에는 `@Component` 가 들어 있다. 그래서 예전에 만든 `AppConfig`·`TestConfig` 도 스캔 대상이 된다.
  - 그러면 그 안의 `@Bean` 들까지 다시 등록되고 실행돼 버린다.
  - 예전 예제 코드를 지우지 않고 남겨 두려고 뺀 것이다. **보통은 설정 정보를 스캔에서 빼지 않는다**(91쪽 참고).

### 각 클래스에 `@Component`, 생성자에 `@Autowired`

```java
@Component
public class MemoryMemberRepository implements MemberRepository {}

@Component
public class RateDiscountPolicy implements DiscountPolicy {}
```

```java
@Component
public class OrderServiceImpl implements OrderService {

    private final MemberRepository memberRepository;
    private final DiscountPolicy discountPolicy;

    @Autowired
    public OrderServiceImpl(MemberRepository memberRepository, DiscountPolicy discountPolicy) {
        this.memberRepository = memberRepository;
        this.discountPolicy = discountPolicy;
    }
}
```

**왜 `@Autowired` 가 필요한가?**
- AppConfig 에서는 `new OrderServiceImpl(memberRepository(), discountPolicy())` 처럼 무엇을 넣을지 설정 클래스가 적어 줬다.
- 이제는 그런 설정 정보 자체가 없다. 그래서 **"이 생성자에 맞는 빈을 넣어 달라"는 표시를 클래스 안에** 해야 한다(92쪽).

### 동작 순서 (93~94쪽 그림)

1. **스캔·등록**: 컨테이너가 만들어질 때 `@Component` 클래스 4개를 찾아 빈 저장소에 등록한다.
   - 빈 이름 기본 규칙: **클래스 이름의 첫 글자만 소문자** — `MemberServiceImpl` → `memberServiceImpl`
   - 직접 지정: `@Component("memberService2")`
2. **자동 주입**: 생성자에 `@Autowired` 가 있으면, 스프링이 **파라미터 타입**으로 빈 저장소에서 빈을 찾아 넣는다.
   - `getBean(MemberRepository.class)` 를 대신 해 준다고 이해하면 된다.
   - 파라미터가 여러 개여도 모두 찾아서 넣는다.

### 테스트 — 사용하는 쪽은 그대로

```java
@Test
void basicScan() {
    ApplicationContext ac = new AnnotationConfigApplicationContext(AutoAppConfig.class);
    MemberService memberService = ac.getBean(MemberService.class);
    assertThat(memberService).isInstanceOf(MemberService.class);
}
```

로그에 `ClassPathBeanDefinitionScanner - Identified candidate component class: ...` 와 함께 4개 클래스가 찍히면 스캔이 된 것이다.

> **스스로 확인**
> - `AppConfig` 의 `@Bean memberService()` 로 등록하면 빈 이름은? 스캔으로 `MemberServiceImpl` 을 등록하면?
>   → `memberService` / `memberServiceImpl`
> - 자동 등록에서 `@Autowired` 를 빼면 왜 곤란할까? → 생성자에 무엇을 넣을지 알려 줄 곳이 없다 (단, 8-1 의 "생성자가 1개면 생략 가능" 규칙 참고)

## 7-2. 탐색 위치와 기본 스캔 대상 (95~96쪽)

**한 줄 요약**: 스캔 시작 위치를 정할 수 있지만, 설정 클래스를 프로젝트 최상단 패키지에 두고 위치 지정을 생략하는 것이 권장 방식이다.

```java
@ComponentScan(basePackages = "hello.core")
```

| 옵션 | 뜻 |
|---|---|
| `basePackages` | 탐색 시작 패키지. 그 하위를 모두 탐색. `{"hello.core", "hello.service"}` 처럼 여러 개 가능 |
| `basePackageClasses` | 지정한 클래스의 패키지를 시작 위치로 |
| 지정 안 함 | **`@ComponentScan` 이 붙은 설정 클래스의 패키지**가 시작 위치 |

- **권장 방법**: 메인 설정 클래스를 프로젝트 루트(예: `com.hello`)에 두고 `basePackages` 를 생략한다.
  - 그러면 `com.hello.service`, `com.hello.repository` 처럼 그 아래가 모두 스캔된다.
  - 스프링 부트도 같은 방식이다. `@SpringBootApplication` 을 루트에 두는 것이 관례이고, 그 안에 `@ComponentScan` 이 들어 있다.
- 🔸 그래서 부트 프로젝트에서 **메인 클래스보다 바깥 패키지**(상위나 형제 패키지)에 만든 `@Component` 는 등록되지 않는다. 실무에서 "빈을 못 찾는다"는 오류의 흔한 원인이다.

### 기본 스캔 대상 — 모두 안에 `@Component` 가 들어 있다

```java
@Component
public @interface Service {
}
```

| 애노테이션 | 스캔 대상 외에 스프링이 해 주는 일 |
|---|---|
| `@Component` | (기본) |
| `@Controller` | 스프링 MVC 컨트롤러로 인식 |
| `@Service` | **특별한 처리 없음** — 개발자가 "핵심 비즈니스 로직이 여기 있다"고 알아보게 하는 표시 |
| `@Repository` | 데이터 접근 계층으로 인식하고, **데이터 계층의 예외를 스프링 예외로 변환** |
| `@Configuration` | 설정 정보로 인식하고, **스프링 빈이 싱글톤을 유지하도록** 추가 처리 (섹션 6 내용) |

- 자바에는 애노테이션 상속이 없다. "애노테이션 안의 `@Component` 를 알아보는 것"은 **스프링이 지원하는 기능**이다(96쪽).
- `useDefaultFilters` 옵션을 끄면 위 기본 대상이 빠진다. 이런 옵션이 있다는 정도만 알면 된다.

> **스스로 확인**
> - `@Service` 를 `@Component` 로 바꿔도 동작이 달라질까? → 스캔은 똑같다. `@Service` 는 특별한 처리가 없다
> - `@Repository` 는 `@Component` 와 무엇이 다른가? → 데이터 계층 예외를 스프링 예외로 변환해 준다

## 7-3. 필터 (97~100쪽)

**한 줄 요약**: `includeFilters` 로 스캔 대상을 추가하고 `excludeFilters` 로 뺄 수 있다. 다만 실제로는 거의 쓰지 않는다.

### 직접 만든 애노테이션으로 시험하기 (테스트 코드)

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface MyIncludeComponent {
}
// MyExcludeComponent 도 같은 모양

@MyIncludeComponent
public class BeanA {
}

@MyExcludeComponent
public class BeanB {
}
```

🔸 `@Target(TYPE)` 은 "클래스에 붙이는 애노테이션"이라는 뜻이다. `@Retention(RUNTIME)` 은 실행 중에도 남아 있어서 스프링이 읽을 수 있다는 뜻이다.

```java
@Configuration
@ComponentScan(
        includeFilters = @Filter(type = FilterType.ANNOTATION, classes = MyIncludeComponent.class),
        excludeFilters = @Filter(type = FilterType.ANNOTATION, classes = MyExcludeComponent.class)
)
static class ComponentFilterAppConfig {
}

@Test
void filterScan() {
    ApplicationContext ac = new AnnotationConfigApplicationContext(ComponentFilterAppConfig.class);
    BeanA beanA = ac.getBean("beanA", BeanA.class);
    assertThat(beanA).isNotNull();                               // BeanA 는 등록됨
    assertThrows(NoSuchBeanDefinitionException.class,
            () -> ac.getBean("beanB", BeanB.class));             // BeanB 는 없음
}
```

- `BeanA` 와 `BeanB` 에는 `@Component` 가 없다. 그래도 `BeanA` 는 `includeFilters` 덕분에 등록되고, `BeanB` 는 `excludeFilters` 때문에 빠진다.

### `FilterType` 5가지 (99쪽)

| 타입 | 기준 |
|---|---|
| `ANNOTATION` (기본값) | 애노테이션 |
| `ASSIGNABLE_TYPE` | 지정한 타입과 그 자식 타입 — 예: `BeanA` 도 빼기 → `@Filter(type = ASSIGNABLE_TYPE, classes = BeanA.class)` |
| `ASPECTJ` | AspectJ 패턴 |
| `REGEX` | 정규 표현식 |
| `CUSTOM` | `TypeFilter` 인터페이스를 직접 구현 |

- **강의 결론(100쪽)**: `@Component` 면 충분해서 `includeFilters` 는 쓸 일이 거의 없다. `excludeFilters` 는 가끔 쓴다. 옵션을 바꾸기보다 **스프링 기본 설정에 맞춰 쓰기를 권장**한다.

## 7-4. 중복 등록과 충돌 (100~101쪽)

**한 줄 요약**: 자동 등록끼리 이름이 겹치면 오류가 난다. 수동 등록과 자동 등록이 겹치면 수동이 이기는데, 이 동작이 잡기 어려운 버그를 만들어서 최근 부트는 기본값을 오류로 바꿨다.

| 상황 | 결과 |
|---|---|
| **자동 vs 자동** — 스캔된 두 클래스의 빈 이름이 같음 | `ConflictingBeanDefinitionException` |
| **수동 vs 자동** — `@Bean(name = "memoryMemberRepository")` 와 스캔된 `MemoryMemberRepository` | **수동 빈이 자동 빈을 덮어씀(오버라이딩)** — 로그: `Overriding bean definition for bean 'memoryMemberRepository' ...` |

```java
@Configuration
@ComponentScan(excludeFilters = @Filter(type = FilterType.ANNOTATION, classes = Configuration.class))
public class AutoAppConfig {

    @Bean(name = "memoryMemberRepository")   // 스캔으로 등록된 이름과 같다
    public MemberRepository memberRepository() {
        return new MemoryMemberRepository();
    }
}
```

- **왜 문제인가**: 개발자가 의도해서 덮어쓰는 경우보다, **여러 설정이 꼬여서** 덮어써지는 경우가 대부분이다. 오류 없이 다른 객체가 들어가니 원인을 찾기 어렵다. 강의자료 표현으로 "항상 잡기 어려운 버그는 애매한 버그다"(101쪽).
- **그래서 최근 스프링 부트**는 수동과 자동이 충돌하면 오류를 내도록 기본값을 바꿨다. `CoreApplication` 을 실행하면 아래 메시지가 나온다.

```
Consider renaming one of the beans or enabling overriding by setting
spring.main.allow-bean-definition-overriding=true
```

> **스스로 확인**
> - 수동과 자동이 충돌할 때, 순수 스프링(`AnnotationConfigApplicationContext`)과 스프링 부트의 결과는?
>   → 순수 스프링은 수동이 덮어씀(로그만 남음) / 부트는 기본으로 오류

# 섹션 8. 의존관계 자동 주입 (PDF 102~122쪽)

## 8-1. 다양한 의존관계 주입 방법 (102~106쪽)

**한 줄 요약**: 주입 방법은 4가지다. 기본은 생성자 주입이고, 생성자가 하나뿐이면 `@Autowired` 를 생략할 수 있다.

| 방법 | 특징 | 언제 |
|---|---|---|
| **생성자 주입** | 생성자 호출 시점에 **딱 1번** 호출이 보장됨 | **불변·필수** 의존관계 (기본) |
| 수정자(setter) 주입 | `setXxx()` 로 주입. 자바빈 프로퍼티 규약 | **선택·변경** 가능성이 있는 의존관계 |
| 필드 주입 | 필드에 바로 `@Autowired` | **쓰지 말자** (아래) |
| 일반 메서드 주입 | 아무 메서드에 `@Autowired`. 여러 필드를 한번에 | 거의 쓰지 않음 |

### 생성자 주입 — 생성자가 1개면 `@Autowired` 생략 가능 (103쪽)

```java
@Component
public class OrderServiceImpl implements OrderService {

    private final MemberRepository memberRepository;
    private final DiscountPolicy discountPolicy;

    // 생성자가 딱 1개 → @Autowired 가 없어도 자동 주입 (스프링 빈일 때만)
    public OrderServiceImpl(MemberRepository memberRepository, DiscountPolicy discountPolicy) {
        this.memberRepository = memberRepository;
        this.discountPolicy = discountPolicy;
    }
}
```

### 수정자 주입

```java
@Component
public class OrderServiceImpl implements OrderService {

    private MemberRepository memberRepository;
    private DiscountPolicy discountPolicy;

    @Autowired
    public void setMemberRepository(MemberRepository memberRepository) {
        this.memberRepository = memberRepository;
    }

    @Autowired
    public void setDiscountPolicy(DiscountPolicy discountPolicy) {
        this.discountPolicy = discountPolicy;
    }
}
```

- `@Autowired` 는 기본적으로 주입할 대상이 없으면 오류를 낸다. 없어도 동작하게 하려면 `@Autowired(required = false)` 를 쓴다(→ 8-2).
- **자바빈 프로퍼티 규약**: 필드를 직접 바꾸지 않고 `setXxx`·`getXxx` 메서드로 읽고 쓰는 오래된 자바 관례다.

### 필드 주입 — 쓰지 말자

```java
@Component
public class OrderServiceImpl implements OrderService {

    @Autowired
    private MemberRepository memberRepository;
    @Autowired
    private DiscountPolicy discountPolicy;
}
```

- 코드가 짧아서 끌리지만, **외부에서 값을 바꿀 방법이 없어 테스트하기 힘들다**는 치명적인 단점이 있다(104쪽).
  - 풀어 보면: 스프링 없이 순수 자바 테스트에서 `new OrderServiceImpl()` 로 만들면 두 필드는 `null` 이다.
  - 필드가 `private` 이고 생성자도 setter 도 없으니, 테스트용 객체를 **넣어 줄 통로가 없다.**
  - 결국 DI 프레임워크(스프링) 없이는 아무것도 할 수 없다.
- 예외적으로 써도 되는 곳: 실제 코드와 관계없는 **테스트 코드**, `@Configuration` 같은 스프링 설정 전용 코드.
- 참고: 순수 자바 테스트에서는 `@Autowired` 가 동작하지 않는다. `@SpringBootTest` 처럼 스프링 컨테이너를 테스트에 통합했을 때만 된다.

### `@Bean` 메서드의 파라미터도 자동 주입된다 (105쪽)

```java
@Bean
OrderService orderService(MemberRepository memberRepository, DiscountPolicy discountPolicy) {
    return new OrderServiceImpl(memberRepository, discountPolicy);
}
```

- 수동 등록하는 빈이 **자동 등록된 빈**을 필요로 할 때 이렇게 받으면 된다.
- ⚠️ PDF 코드에는 파라미터 이름이 `memberRepoisitory` 로 오타가 나 있다. 그대로 치면 본문의 `memberRepository` 를 찾지 못해 컴파일 오류가 나니 고쳐서 치자.

### 일반 메서드 주입

```java
@Autowired
public void init(MemberRepository memberRepository, DiscountPolicy discountPolicy) {
    this.memberRepository = memberRepository;
    this.discountPolicy = discountPolicy;
}
```

> **주의(106쪽)**: 자동 주입은 **스프링 컨테이너가 관리하는 빈**에서만 동작한다. `Member` 처럼 빈이 아닌 클래스에 `@Autowired` 를 붙여도 아무 일도 일어나지 않는다.

## 8-2. 옵션 처리 (106~107쪽)

**한 줄 요약**: 주입할 빈이 없어도 동작하게 하는 방법은 세 가지다.

```java
// 1) 호출 자체가 안 됨
@Autowired(required = false)
public void setNoBean1(Member member) {
    System.out.println("setNoBean1 = " + member);
}

// 2) null 이 들어옴
@Autowired
public void setNoBean2(@Nullable Member member) {
    System.out.println("setNoBean2 = " + member);
}

// 3) Optional.empty 가 들어옴
@Autowired(required = false)
public void setNoBean3(Optional<Member> member) {
    System.out.println("setNoBean3 = " + member);
}
```

```
setNoBean2 = null
setNoBean3 = Optional.empty
```

- `Member` 는 스프링 빈이 아니라서 "주입할 대상이 없는" 상황을 만든 것이다.
- `setNoBean1` 은 출력이 없다. 메서드 자체가 호출되지 않았기 때문이다.
- `@Nullable`(`org.springframework.lang`)과 `Optional` 은 스프링 전반에서 지원한다. 생성자 주입에서 특정 파라미터에만 써도 된다.

---

## 8-3. 생성자 주입을 선택해라! (107~109쪽) ★

**한 줄 요약**: 생성자 주입은 **불변**(바뀌지 않음)을 보장하고, **누락**을 컴파일 시점에 잡아 준다. 그래서 거의 모든 DI 프레임워크가 권장한다.

### 이유 1. 불변

- 대부분의 의존관계는 한 번 정해지면 애플리케이션이 끝날 때까지 바뀌지 않는다. 오히려 **바뀌면 안 된다.**
- 수정자 주입은 `setXxx` 를 `public` 으로 열어 둬야 한다. 누군가 실수로 바꿀 수 있고, 바꾸면 안 되는 메서드를 열어 두는 건 좋은 설계가 아니다.
- 생성자는 객체를 만들 때 **딱 1번**만 호출된다. 그래서 불변으로 설계할 수 있다.

### 이유 2. 누락 — 순수 자바 단위 테스트에서 차이가 난다

수정자 주입이면 이렇게 만들어진다:

```java
@Test
void createOrder() {
    OrderServiceImpl orderService = new OrderServiceImpl();   // 컴파일 OK
    orderService.createOrder(1L, "itemA", 10000);             // 실행하면 NPE
}
```

- 스프링 안에서는 `@Autowired` 가 주입할 빈이 없을 때 오류를 내 준다. 하지만 지금은 스프링 없이 순수 자바로만 테스트하고 있다.
- 그래서 **실행은 되는데** `memberRepository`·`discountPolicy` 가 주입되지 않아 NPE 가 난다.
- **생성자 주입이면** 기본 생성자가 없으니 같은 `new OrderServiceImpl()` 이 **컴파일 오류**가 된다. IDE 가 무엇을 넣어야 하는지 바로 알려 준다.

### 이유 3. `final` 을 쓸 수 있다

```java
@Component
public class OrderServiceImpl implements OrderService {

    private final MemberRepository memberRepository;
    private final DiscountPolicy discountPolicy;

    @Autowired
    public OrderServiceImpl(MemberRepository memberRepository, DiscountPolicy discountPolicy) {
        this.memberRepository = memberRepository;
        // discountPolicy 대입을 빠뜨림
    }
}
```

```
java: variable discountPolicy might not have been initialized
```

- `final` 필드는 생성자에서 반드시 값을 넣어야 한다. 빠뜨리면 **컴파일 시점**에 잡힌다.
- 강의자료 표현: **"컴파일 오류는 세상에서 가장 빠르고, 좋은 오류다!"**(109쪽)
- 수정자·필드·일반 메서드 주입은 모두 **생성자 이후**에 호출되므로 `final` 을 쓸 수 없다. `final` 은 **생성자 주입만** 쓸 수 있다.

### 정리 (109쪽)

- 생성자 주입은 프레임워크에 기대지 않고 순수 자바 언어의 특징을 살리는 방법이다.
- **기본은 생성자 주입**, 필수가 아닌 의존관계는 수정자 주입으로 옵션을 준다. 둘을 함께 써도 된다.
- 필드 주입은 쓰지 않는 게 좋다.

> 🔸 지난주 발표 4번 슬라이드 대본("`final` 이 없으면 컴파일은 통과하고 실행 중에 NPE, `final` 이 있으면 빠뜨렸을 때 컴파일 오류, 7장에서 다시 나온다")이 바로 이 절이다.

## 8-4. 롬복과 최신 트랜드 (109~112쪽)

**한 줄 요약**: 생성자가 1개면 `@Autowired` 를 빼고, 롬복의 `@RequiredArgsConstructor` 로 생성자 코드까지 없앤다. 컴파일된 결과는 직접 쓴 코드와 똑같다.

```java
// 1단계: 기본 — @Autowired 생성자
// 2단계: 생성자가 1개 → @Autowired 생략 (8-1)
// 3단계: 롬복
@Component
@RequiredArgsConstructor
public class OrderServiceImpl implements OrderService {

    private final MemberRepository memberRepository;
    private final DiscountPolicy discountPolicy;
}
```

- `@RequiredArgsConstructor` 는 **`final` 이 붙은 필드를 모아 생성자를 만들어 준다.** 코드에는 안 보이지만 실제로 호출할 수 있다.
- 롬복은 자바의 **애노테이션 프로세서**로 **컴파일 시점**에 생성자 코드를 넣는다. `.class` 파일을 열어 보면 생성자가 그대로 들어 있다(111쪽).
- **최근 방식**: 생성자를 하나만 두고 `@Autowired` 를 생략 + `@RequiredArgsConstructor`. 기능은 다 있고 코드는 깔끔하다.

### 롬복 설정 (111~112쪽)

- PDF 의 `build.gradle` 은 부트 2.3 시절 예제다. 핵심은 아래 의존성 네 줄이다.

```groovy
compileOnly 'org.projectlombok:lombok'
annotationProcessor 'org.projectlombok:lombok'
testCompileOnly 'org.projectlombok:lombok'
testAnnotationProcessor 'org.projectlombok:lombok'
```

- IntelliJ 설정:
  1. 롬복 플러그인 설치
  2. Settings → Annotation Processors → **Enable annotation processing** 체크
  3. 아무 클래스에 `@Getter`·`@Setter` 를 붙여 동작 확인
- 🔸 지금 start.spring.io 에서 Lombok 의존성을 고르면 위 설정이 자동으로 들어가고, 최근 IntelliJ 는 롬복 플러그인을 기본으로 포함한다.

## 8-5. 조회 빈이 2개 이상 — 문제 (112~113쪽)

**한 줄 요약**: `@Autowired` 는 **타입**으로 찾는다. 같은 타입의 빈이 2개 이상이면 무엇을 넣을지 몰라 오류가 난다.

```java
@Component
public class FixDiscountPolicy implements DiscountPolicy {}

@Component
public class RateDiscountPolicy implements DiscountPolicy {}
```

```java
@Autowired
private DiscountPolicy discountPolicy;   // ac.getBean(DiscountPolicy.class) 와 비슷하게 동작
```

```
NoUniqueBeanDefinitionException: No qualifying bean of type
'hello.core.discount.DiscountPolicy' available: expected single matching bean
but found 2: fixDiscountPolicy,rateDiscountPolicy
```

- 오류 메시지가 "하나를 기대했는데 2개를 찾았다"고 두 빈 이름까지 알려 준다.
- **하위 타입(`RateDiscountPolicy`)으로 받으면?** **DIP 를 위배**하고 유연성이 떨어진다. 이름만 다르고 타입이 완전히 같은 빈이 2개일 때는 해결도 안 된다.
- 수동 등록으로 풀어도 되지만, 자동 주입 안에서 해결하는 방법이 세 가지 있다 → 8-6.

## 8-6. `@Autowired` 필드 명, `@Qualifier`, `@Primary` (113~117쪽) ★

### 해결 1. 필드 명(파라미터 명) 매칭

```java
@Autowired
private DiscountPolicy rateDiscountPolicy;   // 필드 이름을 빈 이름과 같게
```

- `@Autowired` 는 ① **타입**으로 먼저 찾는다. ② 결과가 2개 이상이면 **필드 이름·파라미터 이름**으로 빈 이름을 한 번 더 맞춘다.
- 이름 매칭은 **타입 매칭 결과가 여러 개일 때만 추가로** 동작한다.

### 해결 2. `@Qualifier` — 추가 구분자

```java
@Component
@Qualifier("mainDiscountPolicy")
public class RateDiscountPolicy implements DiscountPolicy {}

@Component
@Qualifier("fixDiscountPolicy")
public class FixDiscountPolicy implements DiscountPolicy {}
```

```java
@Autowired
public OrderServiceImpl(MemberRepository memberRepository,
                        @Qualifier("mainDiscountPolicy") DiscountPolicy discountPolicy) {
    this.memberRepository = memberRepository;
    this.discountPolicy = discountPolicy;
}
```

- 등록할 때와 주입할 때 **같은 구분자**를 붙인다. **빈 이름을 바꾸는 게 아니다.**
- 찾는 순서: ① `@Qualifier` 끼리 매칭 → ② 없으면 그 문자열과 같은 **빈 이름** → ③ 그래도 없으면 `NoSuchBeanDefinitionException`
- 강의 경험담: ②에 기대지 말고 **`@Qualifier` 는 `@Qualifier` 를 찾는 용도로만** 쓰는 게 명확하다.
- `@Bean` 으로 수동 등록할 때도 `@Qualifier("mainDiscountPolicy")` 를 똑같이 붙일 수 있다.
- ⚠️ PDF 의 수정자 예시는 `public DiscountPolicy setDiscountPolicy(...)` 인데 `return` 이 없다. 그대로 치면 컴파일 오류가 나니 `void` 로 고쳐서 치자.

### 해결 3. `@Primary` — 우선권

```java
@Component
@Primary
public class RateDiscountPolicy implements DiscountPolicy {}

@Component
public class FixDiscountPolicy implements DiscountPolicy {}
```

- 여러 빈이 매칭되면 `@Primary` 가 붙은 빈이 들어간다. 주입받는 쪽 코드는 손대지 않는다.

### 무엇을 쓸까?

- **`@Qualifier` 의 단점**: 주입받는 **모든 곳**에 `@Qualifier` 를 붙여야 한다. `@Primary` 는 그럴 필요가 없다.
- **활용 예(116~117쪽)**:
  - 자주 쓰는 **메인 DB 커넥션 빈**에는 `@Primary` → 쓰는 곳에서 아무것도 안 붙여도 메인이 들어온다.
  - 가끔 쓰는 **서브 DB 커넥션 빈**은 `@Qualifier` 로 명시해서 받는다.
- **둘 다 있으면?** **`@Qualifier` 가 이긴다.**
  - 스프링의 원칙은 "자동보다 수동, **넓은 범위보다 좁은 범위**의 선택이 우선"이다.
  - `@Primary` 는 기본값처럼 넓게 동작하고, `@Qualifier` 는 콕 집어 상세하게 동작한다.

| 방법 | 어디에 붙이나 | 특징 |
|---|---|---|
| 필드·파라미터 명 | 주입받는 쪽 이름 | 타입 결과가 2개 이상일 때만 추가 동작 |
| `@Qualifier` | 등록하는 쪽 + **주입받는 모든 쪽** | 콕 집어 지정, 우선순위 높음 |
| `@Primary` | 등록하는 쪽만 | 기본값 역할, 주입받는 쪽 수정 없음 |

## 8-7. 애노테이션 직접 만들기 (117~118쪽)

**한 줄 요약**: `@Qualifier("mainDiscountPolicy")` 의 문자열은 오타가 나도 컴파일러가 못 잡는다. 그래서 전용 애노테이션을 만든다.

```java
@Target({ElementType.FIELD, ElementType.METHOD, ElementType.PARAMETER,
        ElementType.TYPE, ElementType.ANNOTATION_TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Qualifier("mainDiscountPolicy")
public @interface MainDiscountPolicy {
}
```

```java
@Component
@MainDiscountPolicy
public class RateDiscountPolicy implements DiscountPolicy {}

@Autowired
public OrderServiceImpl(MemberRepository memberRepository,
                        @MainDiscountPolicy DiscountPolicy discountPolicy) {
    this.memberRepository = memberRepository;
    this.discountPolicy = discountPolicy;
}
```

- 이제 `@MainDiscountPolicy` 를 잘못 쓰면 **컴파일 오류**가 난다. IDE 에서 사용처를 찾기도 쉽다.
- 애노테이션에는 상속이 없다. 여러 애노테이션을 모아 쓰는 것은 **스프링이 지원하는 기능**이다(7-2와 같은 원리).
- `@Autowired` 도 재정의할 수 있지만, 뚜렷한 목적 없이 스프링 기능을 재정의하면 유지보수가 더 혼란스러워진다.

## 8-8. 조회한 빈이 모두 필요할 때 — List, Map (118~120쪽)

**한 줄 요약**: 같은 타입의 빈을 **전부** 받고 싶으면 `List` 나 `Map` 으로 받는다. 클라이언트가 할인 종류를 고르는 **전략 패턴**을 간단히 만들 수 있다.

```java
static class DiscountService {

    private final Map<String, DiscountPolicy> policyMap;
    private final List<DiscountPolicy> policies;

    public DiscountService(Map<String, DiscountPolicy> policyMap, List<DiscountPolicy> policies) {
        this.policyMap = policyMap;
        this.policies = policies;
    }

    public int discount(Member member, int price, String discountCode) {
        DiscountPolicy discountPolicy = policyMap.get(discountCode);   // 코드로 정책 고르기
        return discountPolicy.discount(member, price);
    }
}
```

```java
@Test
void findAllBean() {
    ApplicationContext ac = new AnnotationConfigApplicationContext(AutoAppConfig.class, DiscountService.class);
    DiscountService discountService = ac.getBean(DiscountService.class);
    Member member = new Member(1L, "userA", Grade.VIP);

    int discountPrice = discountService.discount(member, 10000, "fixDiscountPolicy");

    assertThat(discountPrice).isEqualTo(1000);   // VIP 정액 할인 1000원
}
```

### 주입되는 값

| 타입 | 들어오는 것 |
|---|---|
| `Map<String, DiscountPolicy>` | 키 = **빈 이름**(`fixDiscountPolicy`, `rateDiscountPolicy`), 값 = 그 빈 |
| `List<DiscountPolicy>` | `DiscountPolicy` 타입 빈 전부 |
| 해당 타입 빈이 없으면 | 빈 컬렉션·빈 `Map` |

- 흐름: `"fixDiscountPolicy"` 가 넘어오면 map 에서 그 빈을 꺼내 실행한다. `"rateDiscountPolicy"` 면 정률 할인을 실행한다.
- **참고**: `new AnnotationConfigApplicationContext(AutoAppConfig.class, DiscountService.class)` 는 두 가지를 한번에 한다.
  1. 스프링 컨테이너를 만든다.
  2. 넘긴 두 클래스를 **스프링 빈으로 자동 등록**한다. `DiscountService` 에 `@Component` 가 없어도 빈이 되는 이유다.

## 8-9. 자동, 수동의 올바른 실무 운영 기준 (120~122쪽) ★

**한 줄 요약**: **자동이 기본**이다. 단, 직접 등록하는 **기술 지원 객체**와 **다형성을 적극 쓰는 비즈니스 로직**은 수동 등록으로 설정에 드러낸다.

### 왜 자동이 기본인가

- 스프링은 갈수록 자동을 선호한다. `@Controller`·`@Service`·`@Repository` 로 계층별 로직을 자동 스캔하고, 부트는 컴포넌트 스캔이 기본이며 여러 빈을 조건에 맞으면 자동 등록한다.
- `@Component` 한 줄이면 끝날 일을, 설정 클래스에 가서 `@Bean` 을 적고 객체를 만들고 주입 대상을 일일이 적는 건 번거롭다. 빈이 많아지면 설정 관리 자체가 부담이다.
- **결정적으로 자동 등록을 써도 OCP·DIP 를 지킬 수 있다.**

### 그럼 수동은 언제?

| | 업무 로직 빈 | 기술 지원 빈 |
|---|---|---|
| 예 | 컨트롤러, 서비스, 리포지토리 | DB 연결, 공통 로그 처리, AOP 같은 공통 관심사 |
| 특징 | 숫자가 많고 패턴이 비슷함. 문제가 나면 어디인지 잘 보임 | 숫자는 적지만 애플리케이션 **전반**에 영향. 적용되고 있는지조차 알기 어려움 |
| 권장 | **자동** | **수동** — 설정 정보에 딱 드러나게 |

- **다형성을 적극 쓰는 비즈니스 로직**: 8-8 의 `Map<String, DiscountPolicy>` 를 남이 짠 코드로 받았다고 생각해 보자.
  - 어떤 빈이 어떤 이름으로 들어오는지 코드만 봐서는 모른다. 자동 등록이라 여러 파일을 찾아봐야 한다.
  - 이럴 땐 **수동으로 모아 등록**하거나, 자동으로 하더라도 **구현 빈들을 특정 패키지에 묶어 둔다.** 핵심은 "딱 보고 이해가 되어야 한다."

```java
@Configuration
public class DiscountPolicyConfig {

    @Bean
    public DiscountPolicy rateDiscountPolicy() {
        return new RateDiscountPolicy();
    }

    @Bean
    public DiscountPolicy fixDiscountPolicy() {
        return new FixDiscountPolicy();
    }
}
```

- **예외**: 스프링·부트가 자동으로 등록하는 빈(예: 부트의 `DataSource`)은 매뉴얼대로, 부트가 의도한 대로 쓰면 된다.
  - 반대로 **부트가 아니라 내가 직접** 기술 지원 객체를 빈으로 등록한다면 수동 등록으로 드러낸다.

### 정리 (122쪽)

1. 편리한 자동 기능을 기본으로 사용하자
2. 직접 등록하는 기술 지원 객체는 수동 등록
3. 다형성을 적극 활용하는 비즈니스 로직은 수동 등록을 고민해 보자

> 🔸 실무 연결: 지난주 발표 10번에서 본 부트 프로젝트의 `PasswordEncoderConfig`(`@Configuration` + `@Bean passwordEncoder()`)가 바로 2번 "직접 등록하는 기술 지원 객체는 수동 등록"의 사례다. 반면 서비스·컨트롤러는 `@Service`·`@Controller` 로 자동 등록한다.

## 발표 준비용 — 핵심 후보와 점검 질문

### 15분에 넣기 좋은 핵심 후보 — 내 발표 범위인 섹션 7·8 기준 (2~4개 고르기)

1. **컴포넌트 스캔 + `@Autowired`** — AppConfig 가 손으로 하던 등록·주입을 자동으로. 빈 이름 규칙의 차이 (7-1)
2. **생성자 주입을 선택하는 이유** — 불변·누락·`final` (8-3)
3. **같은 타입 빈이 2개 이상일 때** — 필드 명 / `@Qualifier` / `@Primary` 와 우선순위 (8-5·8-6)
4. **자동·수동 실무 기준** — 업무 로직은 자동, 기술 지원은 수동 (8-9)

비핵심(짧게 넘기거나 빼기 좋은 것): 필터(7-3), 옵션 처리(8-2), 애노테이션 직접 만들기(8-7), 롬복 설정 방법

### 섹션 6 점검 질문 (답은 펼쳐서 확인)

<details><summary>A. 싱글톤 패턴이 DIP 를 위반하는 이유는?</summary>

쓰는 쪽이 `SingletonService.getInstance()` 처럼 구체 클래스 이름을 직접 불러야 하기 때문이다 (77쪽).
</details>

<details><summary>B. 스프링 컨테이너가 싱글톤 패턴 코드 없이 객체를 하나로 관리하는 기능의 이름은?</summary>

싱글톤 레지스트리 (78쪽).
</details>

<details><summary>C. 싱글톤 빈에 <code>private int price;</code> 같은 필드를 두고 주문마다 값을 저장하면 어떤 일이 생기나?</summary>

여러 사용자가 같은 객체의 필드를 공유하므로, 다른 사용자의 값이 덮어써진다. 예제에서 A 는 10000원을 주문했는데 20000원을 보게 된다. 지역변수·파라미터로 바꿔 무상태로 설계해야 한다 (80~81쪽).
</details>

<details><summary>D. AppConfig 에서 <code>memberRepository()</code> 가 여러 곳에서 호출되는데도 객체가 하나인 이유는?</summary>

`@Configuration` 이 붙으면 스프링이 CGLIB 로 AppConfig 를 상속한 자식 클래스를 만들어 빈으로 등록한다. 그 클래스의 `@Bean` 메서드는 컨테이너에 빈이 이미 있으면 새로 만들지 않고 그 빈을 돌려준다 (86~87쪽).
</details>

<details><summary>E. <code>@Configuration</code> 을 빼고 <code>@Bean</code> 만 남기면?</summary>

빈 등록은 되지만, `memberRepository()` 가 3번 호출되어 서로 다른 인스턴스가 생긴다. 싱글톤이 보장되지 않는다 (88쪽).
</details>

### 섹션 7·8 점검 질문 (답은 펼쳐서 확인)

<details><summary>1. <code>@Service</code> 와 <code>@Component</code> 는 스캔에서 차이가 있나?</summary>

없다. `@Service` 안에 `@Component` 가 들어 있고, 특별한 처리도 하지 않는다. 비즈니스 계층이라는 표시일 뿐이다 (96쪽).
</details>

<details><summary>2. 스캔으로 등록한 <code>OrderServiceImpl</code> 의 빈 이름은?</summary>

`orderServiceImpl` — 클래스 이름의 첫 글자만 소문자 (93쪽).
</details>

<details><summary>3. 순수 스프링에서 수동 빈과 자동 빈의 이름이 같으면? 부트에서는?</summary>

순수 스프링: 수동 빈이 덮어쓴다(로그만 남음). 부트: 기본으로 오류. `spring.main.allow-bean-definition-overriding=true` 로 바꿀 수 있다 (101쪽).
</details>

<details><summary>4. 생성자가 하나뿐인 스프링 빈에서 <code>@Autowired</code> 를 빼면?</summary>

그래도 자동 주입된다. 스프링 빈일 때만 해당한다 (103쪽).
</details>

<details><summary>5. 필드 주입이 테스트하기 어려운 이유를 한 문장으로?</summary>

`private` 필드에 생성자도 setter 도 없어서, 스프링 없이 만든 객체에 테스트용 객체를 넣을 통로가 없기 때문이다 (104쪽).
</details>

<details><summary>6. 수정자 주입 클래스를 순수 자바 테스트에서 <code>new</code> 로 만들면? 생성자 주입이면?</summary>

수정자 주입: 컴파일은 되고 실행 중 NPE. 생성자 주입: 기본 생성자가 없어서 `new OrderServiceImpl()` 자체가 컴파일 오류 (108쪽).
</details>

<details><summary>7. <code>@Primary</code> 와 <code>@Qualifier</code> 가 함께 있으면 어느 쪽이 이기나? 왜?</summary>

`@Qualifier`. 스프링은 넓은 범위(기본값 역할의 `@Primary`)보다 좁은 범위(콕 집는 `@Qualifier`)의 선택을 우선한다 (117쪽).
</details>

<details><summary>8. <code>Map&lt;String, DiscountPolicy&gt;</code> 로 주입받으면 키에는 무엇이 들어가나?</summary>

스프링 빈의 이름 (`fixDiscountPolicy`, `rateDiscountPolicy`) (120쪽).
</details>

<details><summary>9. DB 연결 객체를 내가 직접 빈으로 등록한다면 자동? 수동?</summary>

수동. 애플리케이션 전반에 영향을 주는 기술 지원 객체는 설정 정보에 드러나게 수동 등록한다. 단, 부트가 자동 등록하는 `DataSource` 는 부트 의도대로 쓴다 (121~122쪽).
</details>
