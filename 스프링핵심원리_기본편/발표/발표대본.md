## 2. 정률 할인 정책 적용 · 1:00

> 예제는 회원이 상품을 주문하면 등급에 따라 할인해 주는 주문 서비스입니다.
> 여기서 **역할**은 `DiscountPolicy` 인터페이스입니다. `discount(member, price)`, 즉 할인 금액을 돌려준다는 메서드 선언만 있고 계산 방법은 없어요. **구현**은 이 인터페이스를 `implements` 한 클래스로, VIP 1000원을 깎는 `FixDiscountPolicy` 와 10%를 깎는 `RateDiscountPolicy` 두 개입니다.
> 그리고 화면 코드처럼 서비스 필드의 타입도 구현 클래스가 아니라 `DiscountPolicy` 인터페이스로 선언했습니다. 소스 코드에서 역할과 구현은 이렇게 나뉘어 있어요.
> 참고로 프로젝트만 스프링 부트로 만들었을 뿐, 여기까지는 **스프링 없는 순수 자바** 코드입니다.
> 그런데 오픈 직전에 기획자가 정률 10% 할인으로 바꿔 달라고 합니다. 오른쪽처럼 `RateDiscountPolicy` 로 바꾸면 되는데요.
> 위 질문입니다. 역할과 구현을 나눴는데, 왜 사용하는 쪽인 `OrderServiceImpl` 을 열어서 고쳐야 할까요? 생각나는 대로 채팅에 써 주세요.

## 3. 구현까지 의존하는 문제 · 1:20 【핵심】

> 강의자료의 실제 의존관계 그림입니다.
> `OrderServiceImpl` 은 위쪽 화살표처럼 `DiscountPolicy` 인터페이스에 의존합니다. 여기까지는 의도한 대로예요.
> 그런데 아래 화살표를 보시면, `new FixDiscountPolicy()` 한 줄 때문에 **구체 클래스에도 의존**하고 있습니다. 이 한 줄을 세 관점으로 보겠습니다.
> 첫째 DIP. 추상화에 의존해야지 구체화에 의존하면 안 된다는 원칙인데, 구체 클래스를 직접 알고 있으니 **DIP 위반**입니다.
> 둘째 OCP. 확장에는 열려 있고 변경에는 닫혀 있어야 하는데, 정률 할인을 추가하려니 사용하는 코드를 고쳐야 했죠. **OCP 위반**입니다.
> 셋째 SRP. 이 클래스는 할인을 적용해 주문을 만드는 일을 해야 하는데, 어떤 구현을 쓸지 고르고 생성하는 일까지 하고 있습니다. 책임이 둘이라 **SRP 위반**입니다.
> 세 위반의 원인은 모두 아래 문장, 이 `new` 한 줄입니다.

**강조**
- 오른쪽 세 줄은 **DIP → OCP → SRP 순서**로. 6번 슬라이드에서 같은 순서로 "충족"을 말합니다.
- 아래 화살표(구체 클래스로 가는 선)를 가리키며 시작하세요.

## 4. 생성자 주입 · 1:30

> 그럼 `new` 를 지우면 어떨까요? 왼쪽처럼 인터페이스만 남기면 DIP 는 지킨 것처럼 보입니다.
> 여기서 컴파일 오류가 나지 않을까 싶으실 텐데, 나지 않습니다. 값을 넣지 않은 객체 필드는 자바가 기본값 `null` 로 채워 주기 때문에 문법상 문제가 없어요.
> 문제는 실행할 때입니다. `createOrder()` 안에서 `discountPolicy.discount(...)` 를 호출하는 순간, null 에 메서드를 호출하니까 NullPointerException 이 납니다. 컴파일은 통과하고 **실행 중에** 터지는 거죠.
> 참고로 강의 코드도 이 줄에서만 `final` 을 뺐습니다. `final` 을 붙이면 값을 넣는 곳이 없어서 이번엔 **컴파일 오류**가 나기 때문이에요.
> 위 질문입니다. 그럼 구현 객체는 누가 넣어 줘야 할까요? 채팅으로 답해 주세요.
> (5~8초 기다린다 — 채팅)
> 답은 **외부의 누군가**입니다. 오른쪽처럼 생성자로 받기만 합니다.
> 오른쪽 필드에 `final` 을 붙인 이유는 두 가지입니다. 첫째, `final` 필드는 생성자에서 반드시 값을 넣어야 해서, 주입을 빠뜨리면 실행 전에 **컴파일 오류**로 알려 줍니다. 왼쪽처럼 실행하다 NPE 가 나는 걸 미리 막는 거예요. 둘째, 한 번 넣으면 바꿀 수 없어서 실행 도중에 다른 구현으로 바뀔 일이 없습니다. 이 내용은 7장 생성자 주입에서 다시 나옵니다.
> 이제 `OrderServiceImpl` 은 어떤 구현이 들어올지 모르고, 자기 일인 주문 생성에만 집중합니다. 무엇을 넣을지는 다음 장의 AppConfig 가 정합니다.

**강조**
- 질문 후 **반드시 기다리세요.**
- 대비를 분명히 — `final` 없음: 컴파일 통과 → 실행 중 NPE / `final` 있음: 빠뜨리면 컴파일 오류.

## 5. AppConfig · 1:00

> AppConfig 는 애플리케이션이 어떻게 동작할지 구성하는 설정 클래스입니다. 하는 일은 두 가지, 구현 객체를 **생성**하고 생성자로 **연결**하는 것입니다.
> `orderService()` 를 보시면 `OrderServiceImpl` 을 만들면서 저장소와 할인 정책을 생성자로 넣어 줍니다. 이렇게 외부에서 넣어 주는 것을 의존관계 주입, **DI** 라고 합니다.
> 코드는 리팩터링한 버전입니다. 메서드 이름이 역할, 반환하는 객체가 구현이라서, 어떤 역할에 어떤 구현을 쓰는지 한눈에 보여요.
> 여러 곳에 있던 `new MemoryMemberRepository()` 중복도 메서드 하나로 모았습니다.
> 강의는 AppConfig 를 공연 기획자에 비유합니다. 배우인 서비스는 자기 배역만 연기하고, 배역에 맞는 배우를 고르는 건 기획자가 한다는 뜻이에요.
> 이제 처음 문제였던 할인 정책 변경이 어떻게 되는지 보겠습니다.

## 6. 사용 영역과 구성 영역 · 1:20 【핵심】

> AppConfig 가 등장하면서 애플리케이션이 그림처럼 둘로 나뉘었습니다. 위는 객체를 쓰는 **사용 영역**, 아래는 객체를 만들고 연결하는 **구성 영역**입니다.
> 정액에서 정률로 바꾸면, 아래 빨간 X 처럼 AppConfig 가 `FixDiscountPolicy` 대신 `RateDiscountPolicy` 를 생성할 뿐입니다. `discountPolicy()` 의 반환 한 줄이에요.
> 앞의 위반 세 가지를 같은 순서로 다시 보겠습니다.
> DIP. 서비스는 이제 `DiscountPolicy` 인터페이스만 압니다. 구체 클래스는 AppConfig 가 골라서 넣어 줍니다.
> OCP. 정책을 바꿔도 사용 영역의 코드는 하나도 바뀌지 않습니다.
> SRP. 생성과 연결은 AppConfig, 서비스는 실행만 합니다. 책임이 나뉘었어요.
> 주의할 점은, 고칠 코드가 없어진 게 아니라는 겁니다. 구성 영역은 당연히 바뀝니다. **고칠 곳이 사용 영역에서 구성 영역 한 곳으로 옮겨간 것**이에요.

**강조**
- 3번 슬라이드와 **같은 순서**(DIP → OCP → SRP)로 "위반 → 충족"을 대비하세요.
- 마지막 문장(고칠 곳이 옮겨갔다)에 무게를. "코드를 안 고쳐도 된다"로 말하지 마세요.

## 7. 정적 의존관계와 동적 의존관계 · 1:30 【핵심】

> 그럼 서비스 코드는 그대로인데 동작은 어떻게 바뀌는 걸까요? 강의는 의존관계를 두 가지로 나눠서 봅니다.
> 왼쪽 **정적인 클래스 의존관계**는 소스 코드에 적힌 의존입니다. `OrderServiceImpl.java` 의 import 와 필드 타입만 봐도 `MemberRepository`, `DiscountPolicy` 두 인터페이스를 쓴다는 걸 실행하지 않고 알 수 있어요.
> 오른쪽 **동적인 객체 의존관계**는 프로그램이 실행된 뒤 메모리에 실제로 만들어진 객체끼리의 연결입니다. `discountPolicy` 필드에 정액 할인 객체가 들어 있는지 정률 할인 객체가 들어 있는지는, 코드만 봐서는 모르고 실행해야 정해집니다.
> 여기서 실행 시점은 `main()` 에서 `appConfig.orderService()` 를 호출하는 순간입니다. 스프링을 쓰면 애플리케이션이 시작되면서 컨테이너가 만들어지는 순간이고요.
> 그 순간 AppConfig 가 `new FixDiscountPolicy()` 로 힙에 객체를 만들고, 그 객체의 **참조값**을 `OrderServiceImpl` 생성자에 넘깁니다. 서비스 필드에는 그 참조값이 저장되고요. 이렇게 외부가 객체를 만들어 참조를 넣어 주는 것이 **DI** 입니다.
> 그래서 정률 할인으로 바꿀 때 **그대로 두는 것**은 `OrderServiceImpl` 의 소스 코드, 즉 import 와 필드 타입입니다. **바뀌는 것**은 실행할 때 그 필드가 가리키는 객체가 정액 객체에서 정률 객체로 바뀌는 것뿐이고, 그건 AppConfig 한 줄이 정합니다.
> 이렇게 제어 흐름을 서비스가 아니라 외부가 쥐는 것을 **제어의 역전, IoC**, 객체를 생성하고 연결해 주는 AppConfig 같은 것을 **DI 컨테이너**라고 부릅니다. 다음 장에서 이 DI 컨테이너를 스프링으로 바꿉니다.

**강조**
- "왼쪽 그림 / 오른쪽 그림"을 번갈아 가리키며. 정적은 그대로, 동적만 바뀐다가 핵심입니다.
- IoC 는 화면에 없습니다 — 대사로만 짚고 아래 결론 띠로 마무리하세요.

## 8. AppConfig에서 스프링 빈으로 · 1:00

> 지금까지는 순수 자바였습니다. 이제 스프링으로 바꿔 보겠습니다.
> 왼쪽은 개발자가 AppConfig 를 `new` 하고 메서드를 직접 호출해서 서비스를 꺼냈습니다.
> 오른쪽은 AppConfig 에 `@Configuration` 을, 각 메서드에 `@Bean` 을 붙입니다. 바뀐 건 애노테이션 두 종류뿐이에요.
> 그리고 `ApplicationContext`, 즉 **스프링 컨테이너**를 만들 때 AppConfig 를 설정 정보로 넘깁니다. 컨테이너는 `@Bean` 이 붙은 메서드를 모두 호출해서 반환된 객체를 등록하는데, 이 객체를 **스프링 빈**이라고 합니다.
> 빈 이름은 기본으로 **메서드 이름**을 씁니다. 그래서 아래처럼 `getBean("memberService", ...)` 로 꺼내요.
> 코드는 조금 늘었지만, 이제 객체를 만들고 연결하는 일은 스프링 컨테이너가 맡습니다.

## 9. 자바 설정과 XML 설정 · 1:10 【핵심】

> 세 번째 덩어리입니다. 방금 본 자바 설정 말고도 빈을 등록하는 방법이 있을까요?
> 강의자료에 따르면 스프링 컨테이너는 자바 코드, XML, Groovy 등 여러 형식의 설정을 받을 수 있게 설계되어 있습니다. 강의에서 직접 다루는 건 왼쪽 **자바 설정**과 오른쪽 **XML 설정** 두 가지예요.
> 두 코드를 나란히 보시면, `@Bean` 메서드 하나가 `<bean>` 태그 하나에 대응합니다. 메서드 이름이 `id` 가 되고, 생성자로 넣던 저장소는 `<constructor-arg>` 의 `ref` 로 연결합니다.
> 다른 건 아래 컨테이너 클래스입니다. 자바 설정은 `AnnotationConfigApplicationContext` 에, XML 은 `GenericXmlApplicationContext` 에 설정을 넘깁니다. 둘 다 `ApplicationContext` 의 구현체예요.
> 강의자료 기준으로 요즘은 스프링 부트와 함께 자바 설정을 주로 쓰고, XML 은 레거시 프로젝트에 많이 남아 있습니다. XML 은 컴파일 없이 설정을 바꿀 수 있다는 장점도 있어요.
> 중요한 건 어느 쪽이든 `MemberServiceImpl` 같은 서비스 코드는 **그대로**라는 점입니다.

**강조** — XML 의 `...` 은 패키지 생략 표시라고 한마디 하세요.

## 10. 실무 프로젝트의 빈 설정 · 1:10 【실무 · 강의 밖 보충】

> 강의에는 없는 내용을 보충하겠습니다. 제가 다룬 실무 프로젝트에서 **같은 비밀번호 암호화 빈**을 어떻게 등록하고 쓰는지 보겠습니다.
> 왼쪽 첫 줄, 레거시 프로젝트는 `@Configuration` 이 하나도 없고 빈을 전부 XML 로 등록합니다. 오른쪽 위 블록 첫 줄처럼 `<bean>` 태그로요.
> 왼쪽 둘째 줄, 부트 프로젝트는 반대로 XML 이 없습니다. 오른쪽 아래 블록처럼 `@Bean` 메서드로 등록해요.
> 왼쪽 셋째 줄, 레거시도 섞어 씁니다. XML 안의 `component-scan` 이 `@Service` 가 붙은 클래스를 빈으로 등록합니다. 6장에서 나오는 내용이에요.
> 차이는 꺼내 쓰는 코드입니다. 오른쪽 위 블록 아래 세 줄, 레거시는 빈을 꺼내서 `StandardPasswordEncoder` **구체 클래스로 형변환**합니다. 3번 슬라이드의 구현까지 의존하는 문제 그대로라, 암호화 방식을 바꾸면 이 코드가 있는 곳을 모두 고쳐야 해요.
> 부트는 마지막 줄처럼 `PasswordEncoder` **인터페이스**로 받습니다. 그래서 방식을 바꿀 때 `@Bean` 의 `return` 한 줄만 고치면 됩니다. 왼쪽 아래 문장처럼, 꺼내 쓰는 쪽이 인터페이스로 받아야 바꿔 끼울 수 있습니다.
