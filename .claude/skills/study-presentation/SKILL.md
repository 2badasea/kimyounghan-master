# 스터디 발표자료 생성

매주 월요일 스터디 발표(**상한 15분**)용 **발표자료(.pptx) + 발표대본(.md)** 을 같은 규격으로 만든다.
형식은 이 스킬이 고정하고, 매주 바뀌는 것은 **입력(강의자료 PDF + 사용자 피드백)** 뿐이다.

- **요청 입력 양식**: [references/intake-form.md](references/intake-form.md) — 요청을 받으면 이것부터 보낸다
- 스타일 버전: [references/styles/README.md](references/styles/README.md) — 기본 **v1(토스 블루)**: [v1.md](references/styles/v1.md)
- 덱 스펙(JSON) 작성법: [references/deck-spec.md](references/deck-spec.md)
- 대본·노트 작성 규칙: [references/script-format.md](references/script-format.md)
- 예제: [examples/spring-intro.deck.json](examples/spring-intro.deck.json) — 스프링 입문 발표(실제 발표한 3차 확정본, v1 표본). 새 덱은 이 **구조·말투·스타일**을 기준으로 쓴다. 단 이 예제는 시간·퀴즈 규칙 확정 전 버전이라 **18분·퀴즈 3문제**다 — 새 덱은 아래 규칙(상한 15분, 퀴즈 2문제)을 따른다.
- **완료된 발표의 덱은 다시 만들지 않는다.** 규칙을 정하는 대화에서는 스킬 문서·생성기만 고치고, 지난 발표 폴더의 deck.json·pptx·대본은 건드리지 않는다.

## 핵심 원칙

1. **단일 원본은 덱 스펙(JSON)이다.** pptx와 대본 md는 스펙에서 생성되는 결과물이다. 수정 요청이 오면 **스펙을 고치고 다시 빌드**한다. pptx를 손으로 고치지 않는다.
2. **대사는 두 곳에 같이 들어간다.** 대본 md(전문 + 시간 배분 + 리허설 체크리스트)와 pptx 슬라이드 노트(발표자 보기용 전문 + 연출 메모).
3. **내용은 강의자료 PDF 범위 안에서만** 쓴다. 강의 밖 내용은 실무 사례(본인 경험)로만 넣고, 그렇다고 표시한다.
4. **규격을 바꾸는 피드백**("제목 크기 줄여", "카드 색 바꿔")은 그 덱만 고치지 말고 해당 스타일 버전(`scripts/styles/<버전>.js`)과 `references/styles/<버전>.md` 변경 이력에 반영해 다음 주에도 적용되게 한다. 버전을 갈아엎는 수준이면 새 버전을 만든다([styles/README.md](references/styles/README.md)).
5. **사용자에게 하는 모든 말은 한국어로** 한다(보고·질문·요약 포함).

## 작업 흐름

### 1. 요청 양식 보내기 → 요청서 기록
- 요청을 받으면 바로 만들지 않고 [입력 양식](references/intake-form.md)의 **[보낼 양식]** 을 채팅으로 보낸다. 요청 메시지에 이미 있는 값은 미리 채운다.
- 사용자가 채워 보내면 `<강의 폴더>/발표/요청서.md` 에 기록한다. 스타일 버전이 비어 있으면 **v1**.
- "내가 생각하는 핵심"은 PDF를 읽고 맞는지·빠진 것은 없는지 **피드백을 붙여** 2단계 구성안과 함께 답한다.

### 2. 구성안 합의 (텍스트로만)
PDF를 읽은 뒤 슬라이드 목록을 표로 제시하고 합의를 받는다.

| # | 유형 | 제목(간결한 명사형) | 핵심 메시지 | 시간 |
|---|---|---|---|---|

구성 규칙은 아래 [내용 구성 규칙](#내용-구성-규칙)을 따른다.

### 3. 덱 스펙 작성
- 위치: `<강의 폴더>/발표/deck.json` (예: `C:\BadaDev\kimyounghan\스프링입문\발표\deck.json`)
- `output.dir`은 `"."` (스펙과 같은 폴더에 결과물 생성)
- 유형별 필드는 [deck-spec.md](references/deck-spec.md), 대사는 [script-format.md](references/script-format.md)
- 코드는 **IntelliJ 기본 포매터 기준**(4칸 들여쓰기)으로 정리해서 넣는다. PDF에서 복사한 코드의 깨진 들여쓰기·줄바꿈을 바로잡는다.

### 4. 빌드
```bash
node "C:/BadaDev/kimyounghan/.claude/skills/study-presentation/scripts/build.js" "<강의 폴더>/발표/deck.json"
```
- 처음 쓰는 환경이면 `scripts/`에서 `npm install` 한 번 (pptxgenjs, `node_modules`는 git 제외)
- **산출물은 항상 세 개가 한 벌**이다 (빌드가 자동으로 같이 만든다):

  | 파일 | 용도 |
  |---|---|
  | `<이름>.pptx` | 발표자용 — 노트에 대사 전문 |
  | `<이름>_공유.pptx` | 공유용 — **노트(대본)를 뺀** 같은 슬라이드. 스터디원에게 나눠 줄 때 |
  | `발표대본.md` | 대본 전문 + 시간 배분 + 리허설 체크리스트 |

  - 생성기로 만들지 않은 pptx 도 `node scripts/share.js <파일.pptx>` 로 공유본을 만들 수 있다.
- **파일 이름에 차수(`_2차`, `_3차`, `_최종`)를 붙이지 않는다.** 같은 이름에 덮어쓴다. 이전 차수와 비교가 필요하면 git 기록으로 본다.
  - pptx 가 PowerPoint 에 열려 있어 빌드가 실패(EBUSY)하면 다른 이름으로 우회하지 말고 **사용자에게 닫아 달라고** 한다.
- **git 에는 최종 산출물만 둔다** (위 세 파일 + deck.json·요청서·작업_인계). 렌더 PNG·임시 파일은 scratchpad 에만 만든다. 강의자료 PDF·강의 제공 소스는 올리지 않는다(.gitignore).
- 출력의 **경고를 0건으로 만든다.** 경고는 넘침·과밀·시간 초과를 알려준다. 문장을 줄이거나 슬라이드를 나눠서 해결한다(글자 크기를 최소치 아래로 내리지 않는다).

### 5. 시각 검수 (필수)
```powershell
powershell -ExecutionPolicy Bypass -File "C:/BadaDev/kimyounghan/.claude/skills/study-presentation/scripts/render.ps1" -Pptx "<pptx>" -OutDir "<scratchpad>/render"
```
- PowerPoint로 PNG를 뽑고 `sheet-N.png`(8장씩 모아보기)를 만든다. **sheet를 먼저 보고, 문제 있는 슬라이드만 원본 PNG로 확인**한다.
- PowerPoint가 파일을 여는 단계에서 실패하면 pptx 구조 문제다.
- 확인 항목: 글자 넘침·잘림, 요소 겹침, 코드 블록이 너무 작음(14pt 미만 금지), 제목 위치 일관성, 한 단어가 두 줄로 쪼개짐, 강조색 남용
- **Pretendard가 설치되지 않은 PC에서는 렌더링이 틀어진다**(대체 글꼴로 그려져 줄이 잘림). 검수 전에 설치 여부를 확인한다.

### 6. 전달
- pptx 경로(발표자용·공유용), 대본 md 경로, 장 수·총 시간, 남은 경고를 보고한다.
- 사용자가 최종본이라고 하면 커밋·푸시 여부를 묻는다(요청 없이 커밋하지 않는다).
- 사용자 검수 → 피드백 → **스펙 수정 → 재빌드 → 재검수**를 반복한다.

## 내용 구성 규칙

자바 입문 발표(2026-08)에서 확정한 원칙. 피드백으로 바뀌면 여기를 갱신한다.

- **분량: 상한 15분(넘기지 않는다)**, **12~15장**. 슬라이드당 평균 40~60초. 초안은 **13분 안팎**으로 잡아 보충 요청이 들어올 여유(약 2분)를 남긴다.
- **보충 요청이 오면 시간부터 계산한다.** 보충(강의 밖 내용·설명 추가·슬라이드 추가)을 반영하면서 15분을 넘게 되면, 반영 전에 "이만큼 늘어나니 ○○를 줄이자"고 **줄일 후보와 함께** 제안한다.
- **15분을 넘으면 이 순서로 줄인다 (사용자 결정 2026-10-04, "A안" — 슬라이드는 지우지 않고 대사부터 줄인다).** 시간 숫자만 바꾸지 말고 대사를 실제로 줄인다.
  1. **핵심 주제가 아닌 비교·나열 슬라이드** → 각 0:30. 화면 요점(아래 두 줄·불릿)만 읽고 넘어간다. 예: DB 기술 비교 슬라이드.
  2. **강의 밖 보충 슬라이드** → 0:40. 결론 한 문장 + 차이 한 문장만 남긴다.
  3. **표지·정리** → 각 0:30.
  4. 그래도 넘으면 핵심이 아닌 슬라이드 하나를 앞뒤 슬라이드 대사로 흡수한다 — **이 단계는 사용자 확인 후에만.**
  - 사용자가 고른 **핵심 주제 슬라이드는 줄이지 않는다.**
- **단원은 최대 3개.** 4개 이상이면 단원당 3분도 못 써서 목차 읽기가 된다.
- **표지는 강좌명만 간단하게.** 제목은 강좌명 그대로(예: "스프링 입문"), 소제목에 강의 전체 이름. **발표일은 넣지 않는다.** 하단에는 발표자 이름만.
- **관통 메시지 하나.** 표지 대신 목차 카드·첫 대사·정리 슬라이드가 같은 메시지를 가리키게 한다.
- **면접 질문·예상 질문(qna)은 넣지 않는다.**
- **슬라이드 제목은 단어 위주로 간결하게.** 반말 문장 제목 금지. "오늘 만들 것은 회원 관리 하나다" ✗ → "회원 관리 예제 구조" ✓, "코드가 사라진다" ✗ → "JPA 와 스프링 데이터 JPA" ✓. 강조(`**`)는 쓰지 않아도 된다.
- **"실무에서 중요하다"를 추상적으로 말하지 않는다.** 구체적인 실패 사례로 말한다. 실무 슬라이드(`case`)는 본인 경험으로 채운다.
- **회사 코드는 화면에 띄우지 않는다.** 구조만 재현하고, 클래스명·경로·도메인·발주처는 언급하지 않는다.
- **질문 → 기다림 → 답** 구간을 둔다. 질문은 슬라이드를 따로 만들지 말고 **답이 나오는 슬라이드 상단 띠(`lead`)** 에 둔다. 온라인이라 기다림은 **5~8초**(채팅 입력 시간).
- **화면이 좁으면 슬라이드를 나눈다.** 한 슬라이드에 개념 두 개를 넣지 않는다(예: 빈 등록 두 방법 → 두 장, 왼쪽 코드·오른쪽 특징).
- **개념은 비유어보다 기능·역할로 설명한다.** 인터페이스 = "약속" ✗ → "어떤 기능을 할지 역할(메서드)만 정의" ✓. 스프링 내부 요소(viewResolver, HttpMessageConverter 등)는 "~라는 스프링의 구성 요소가"처럼 정체를 밝혀 말한다.
- **"스프링이 알아서 해준다"류 설명은 단계로 푼다.** 무엇을 보고(예: 생성자 파라미터 타입) → 어디서 찾아(컨테이너) → 무엇을 하는지(생성자에 넣음)를 대사에 쓰고, 필요하면 "개념 코드" 블록으로 스프링이 대신 하는 일을 보여준다.
- **"코드를 안 고쳐도 된다"고 과장하지 않는다.** DI·OCP 는 "고칠 곳이 사용하는 쪽(서비스)에서 조립하는 쪽(설정) 한 곳으로 옮겨간다"로 설명한다.
- **단점은 이유까지.** "테스트가 어렵다" 같은 결론만 쓰지 말고 왜 그런지(예: private 필드라 스프링 없이 넣을 통로가 없다)를 대사에 넣는다.
- **강의 밖 보충**은 사용자가 요청할 때만 넣는다(예: `@RestController`, Lombok). `tag` 에 "강의 밖 보충"을 달고, 대사 첫 줄에서 먼저 밝힌다.
- **정리 슬라이드**는 단원별 한 줄(+ 보조 한 줄)만. 강의 인용·"다음 강의" 안내는 넣지 않는다. 글씨는 크게(제목 24pt).
- **퀴즈는 마지막에 2문제**: `summary` → `quiz-item` × 2. 진행은 **문제 화면 → 각자 생각(20~30초) → 발표자가 넘겨 정답 공개 → 이유 설명**. `quiz-item` 하나가 문제·정답 슬라이드 두 장으로 펼쳐지고, 같은 배치라 넘기면 정답이 드러나는 것처럼 보인다. 정답 이유는 발표 핵심 메시지와 같은 문장이 되게 한다. 퀴즈 2문제에 약 2~3분을 잡는다.
  - **출제 대상은 요청서의 "내가 생각하는 핵심"(합의한 핵심 주제)뿐이다.** 문제마다 어느 핵심 주제를 묻는지 `cues` 에 적는다. 핵심 주제가 아닌 내용(곁가지 개념, 강의 밖 보충)은 아무리 좋아도 출제하지 않는다.
  - 화면에 "생각할 시간" 같은 안내 문구는 넣지 않는다. O/X 문제는 O·X 큰 카드로, 정답 공개 때 정답 카드가 파랗게 바뀐다.
  - **문제는 핵심 주제와 직결되고 조금은 생각하게 하는 것**으로. 발표 결론을 그대로 되묻는 쉬운 회수형 문제는 피한다. 강의자료의 "주의" 문단이 좋은 출제 소재다.
  - **정답 대사(`answerScript`)는 보충 설명까지** 쓴다(3~5문장): 동작 원리, 관련 클래스·개념, 실무에서의 의미.
- **라이브 데모는 하지 않는다.** 막히면 시간 손실이 크다. 실행 결과는 `output` 코드 블록이나 캡처 이미지로 보여준다.
- **밀릴 때 압축할 슬라이드 1장**을 정해 `meta.compress`에 적는다.

## 슬라이드 유형 한눈에

| type | 용도 |
|---|---|
| `cover` | 표지 겸 목차 (단원 카드 2~4개) |
| `statement` | 큰 한 문장 — 훅, 전환 (질문은 `lead` 를 우선) |
| `code-compare` | before/after 코드 비교 + 아래 요점·결론 |
| `code-explain` | 코드(+결과) 왼쪽, 설명 오른쪽 |
| `case` | 실무 사례 — 설명 왼쪽, 코드 오른쪽, "왜?" 질문 박스 |
| `cards` | (코드) + 개념 카드 2~4개 |
| `contrast` | 두 개념 대비 — 회색 카드 vs 파란 카드 |
| `principle` | 핵심 원칙 — 큰 문장 + 코드·결과 + 파란 결론 카드 |
| `image` | 강의자료 그림(다이어그램) + 설명 |
| `summary` | 정리 — 단원별 한 문장 |
| `quiz-item` | 퀴즈 1문제 → [문제, 정답·이유] 두 장으로 펼쳐짐 |

## 온라인(디스코드) 발표 규칙

발표는 디스코드 화면공유로 진행한다. 화면이 압축되고, 청중 반응은 채팅으로만 온다.

- **코드는 14pt 이상, 블록당 12줄 이하.** 넘으면 빌드 경고 — 핵심 줄만 남기거나 슬라이드를 나눈다.
- **질문 대기는 5~8초**, 대사에 "채팅에 답을 써주세요"처럼 답하는 방법을 함께 말한다.
- **퀴즈 생각 시간은 20~30초.** 발표자가 임의로 넘겨 정답을 공개한다.
- **라이브 데모 없음.** IDE로 창을 전환하지 않는다.
- **화면공유는 슬라이드쇼 창만.** 발표자 보기(노트의 대사 전문)는 보조 모니터에 둔다. 모니터가 1대면 대본 md를 휴대폰·태블릿으로 본다.

## 실무 코드 참조 프로젝트

사용자가 **"실무 코드 예시로 보충하라"고 지시할 때만** 참고한다. 지시가 없으면 열어보지 않는다.

| 스펙 | 경로 | 빌드 |
|---|---|---|
| 레거시 + MyBatis + jQuery | `C:\BadaDev\geumcheong_src` | Maven |
| 레거시 + JPA + jQuery | `C:\BadaDev\bucheon` | Maven |
| 부트 + JPA + jQuery | `C:\BadaDev\cali\backend` | Gradle |
| 부트 + JPA + 모던 프론트 | `C:\BadaDev\cali\frontend` | npm |

강의 주제별로 고를 때:
- 레거시 vs 부트 비교(내장 톰캣, 설정 방식) → `geumcheong_src`·`bucheon` vs `cali/backend`
- MyBatis vs JPA 비교 → `geumcheong_src` vs `bucheon`·`cali/backend`
- 계층 구조·DI·트랜잭션 등 부트 기준 예시 → `cali/backend`

**사내 코드 사용 원칙**
- 코드를 그대로 옮기지 않는다. **구조만 재현**하고 클래스명·패키지·테이블명·URL·도메인을 일반 이름(`Member`, `Order` 등)으로 바꾼다.
- 회사명·발주처·서버 주소·계정·개인정보는 화면과 대사 어디에도 넣지 않는다.
- 슬라이드에 "실무 코드를 단순화해 재현"이라고 밝히고, 대본 cues에 "회사 코드·이름 언급 금지"를 넣는다.

## 환경

- Node.js + `scripts/node_modules/pptxgenjs` (`npm install` in `scripts/`)
